# 家长与教师双入口、孩子档案化 MVP 设计

## 背景与目标

当前实现把 `CHILD` 作为可切换的客户端身份。实际 MVP 的孩子通常没有独立手机和微信账号；这会让同一台家长手机上的身份切换、回执、审计与隐私边界变得不必要地复杂。

本次调整将可登录主体收敛为家长与教师。孩子保留独立业务档案和 `childId`，但不再作为登录身份、路由身份或客户端 actor。家长使用自己的微信账号代表已选孩子完成任务、上传作业、查看成长结果；老师继续通过教师激活和分组权限工作。

目标：

- 首次微信进入时，映射或创建一个稳定内部 `userId`（现有 `Account.id`）。
- 家长可创建并管理多个孩子档案；孩子始终有独立 `childId`。
- 每一个孩子相关写操作由 `userId + childId` 审计，服务端重新验证有效监护关系。
- 入口仅展示家长、教师；不再展示、接受或依赖孩子登录身份。
- 不改动真实 CloudBase 环境、密钥或已存数据；所有外部发布/迁移另行按发布门禁执行。

## 不做的事

- 不为孩子创建微信登录账号、手机登录或独立 `userId`。
- 不增加孩子视图、家长 PIN 或家长/孩子模式切换。
- 不改变教师激活、教师工作空间、多分组、邀请码审批的业务语义。
- 不实现未来的孩子独立设备绑定；仅保证未来能将一个账号链接到既有 `childId`，无需数据迁移。

## 身份与数据模型

### 可登录用户

`Account.id` 是系统内部 `userId`。一次微信登录只解析为一个账号：

- 家长能力来自该账号与孩子之间的有效 `GuardianLink`。
- 教师能力来自该账号的已激活教师工作空间、机构成员关系和有效分组角色绑定。
- 同一个人既是家长又是老师时仍使用同一个 `userId`；角色来自关系，不创建重复账号。

### 孩子档案

孩子只有 `Child.id`（即 `childId`）：

- 一个家长账号可新增多个孩子档案。
- 所有 assignment、submission、奖励、分组成员关系、图片资源和 AI 草稿继续以 `childId` 为数据隔离键。
- 孩子档案不是 `ActorContext.mode`，不携带登录证明，也不能单独发起 API 请求。

### 代表操作

此前需要 `CHILD` actor 的能力改为家长账号显式代表孩子执行：

```text
家长 Account(userId)
  + 请求中的 childId
  + 有效 GuardianLink
  + assignment.childId / resource.childId 一致
  => 允许操作
```

审计至少保留操作家长的 `accountId`、目标 `childId`、资源 ID 与请求 ID。`childId` 不从客户端持久化状态隐式信任，所有服务端动作都要验证其与资源和当前监护关系一致。

## 页面与交互

### 入口

启动页只有两个入口：

1. 我是家长
2. 我是教师／助教

家长首次没有孩子时进入家庭创建/添加孩子流程；教师未激活时进入激活页。启动页、角色切换页、MVP 导航和遗留深链均不再提供“我是孩子”。

### 多孩子选择

家长页面保留一个全局可见的“当前孩子”选择器：

- 尚未选中孩子时，先要求明确选择，不能进入任务、提交、奖励或入组操作。
- 已选中后可本地记住最近一次选择，仅作为便利；进入页面和每次服务端操作仍验证该孩子属于当前家长。
- 每个孩子相关页面持续显示当前孩子昵称，避免误把任务提交到另一个孩子。
- 选择器不构成授权，服务端的 `GuardianLink` 校验始终是权威来源。

### 家长代表孩子完成任务

原孩子侧任务、提交、果园与分组页面改为家长已选孩子的子流程，保留孩子数据的展示但使用家长账号请求：

- “完成任务”改为“为孩子提交完成情况”。
- 图片上传、补充提交、查看任务图片、果园操作都需要显式 `childId`。
- 路由可放在家长页面命名空间或由旧孩子路由立即重定向到家长当前孩子页；MVP 的 `app.json` 不保留可直接作为孩子身份工作的页面入口。

## 服务端授权与 API 改造

### Actor 收敛

- 外部 Core API 仅接受已登录成人账号上下文；`mode: CHILD` 统一拒绝为已禁用/不支持的模式。
- 删除 `CHILD_ACTIONS` 作为一类独立权限来源；每个孩子相关 action 直接接受 `childId` 或从 `assignmentId` 推导目标孩子。
- 对资源型动作，先读取资源，再检查 `resource.childId === target childId` 与当前账号的有效监护关系。

### 代表孩子的动作

以下能力必须由 ACCOUNT actor 加有效监护关系实现：

- 今日任务、任务详情、分组、果园、奖励等孩子数据读取。
- 提交任务、补交、任务证据上传/读取、开始/改名/收获果树。
- 任何含 `assignmentId` 的操作必须从 assignment 推导 `childId`，不信任客户端另传的冲突值。

服务保留现有资源级回执与事务幂等：回执上下文必须绑定账号、目标孩子、资源和授权依赖；家长为孩子 A 的回执不能被同账号切换至孩子 B 后重放。

### 家长与教师边界

- 家长只能代表自己有有效监护关系的孩子。
- 教师只可依当前有效机构成员、分组角色、孩子分组成员关系读取或审核相应孩子的数据。
- 机构成员、分组绑定、监护关系或孩子分组成员撤销后，旧回执、图片读取、详情投影和审核均必须重新拒绝。

## 迁移与兼容

该变更不要求迁移已有孩子、任务、图片、提交或奖励数据，因为它们本来都以 `childId` 保存。

- 客户端不再发送 `CHILD` actor。
- 旧孩子路由不保留实际孩子身份能力；统一重定向至家长入口并要求选择孩子，或从 manifest 删除。
- 服务端对旧 `CHILD` 请求明确返回不可用错误，不做静默降级，以避免任意 `childId` 伪造。
- 开发工具产生的本地项目配置不进入功能提交。

## 验收与测试

本地测试至少覆盖：

1. 启动页和角色切换只展示家长、教师。
2. 家长首次创建家庭后可添加多个孩子；选择状态可切换且页面清晰显示当前孩子。
3. 家长代表孩子 A 可读取、提交、上传证据、操作果园；切到孩子 B 后不能读取或重放 A 的资源/回执。
4. 未选择孩子、伪造 childId、失效监护关系均被服务端拒绝。
5. `CHILD` actor 被 API 拒绝；旧孩子路由不可获得孩子权限。
6. 教师激活、多分组、邀请审批、老师审核以及孩子/机构撤权回归不受影响。
7. 家长/老师共享一个 `userId` 时，角色能力仍按关系正确组合。
8. 全量测试、类型检查、Mini Program 编译通过；模拟器至少验证两个入口和家长多孩子选择流程。

云开发环境、真实 OpenID、CloudBase 权限、真机上传和真实 DeepSeek 调用仍是发布前人工门禁，不在本次本地代码变更中执行。
